Open Source Radar

You picked an issue. Now what?

Here's the whole thing in seven steps. Nobody gets it perfect the first time, and maintainers know that. Each step links to the longer guide chapter if you want more detail.

  1. Say you're on it. Leave a short comment on the issue, something like "Hi, I'd like to work on this. My plan is to ...". Some projects assign you, some just want a PR. If the contributing guide says to wait for a reply, wait. Never open a PR on an issue someone else already claimed. Claiming an issue
  2. Read the rules first. Five minutes in CONTRIBUTING.md saves you a closed PR. Look for a CLA to sign, a DCO sign-off, an AI policy and the PR template. Rules before you start
  3. Fork, clone, branch. Fork on GitHub, clone your fork, then make a branch for this one issue (git switch -c fix-typo-in-readme). Don't work on main. Fork and clone, Setup
  4. Get it running before you change anything. Build it and run the tests as they are. If that fails, that's a good question to ask on the issue, not a dead end. Build and test first, Reading a codebase
  5. Make the smallest change that fixes it. Reproduce the problem, add a test if the project has tests, fix only what the issue asks for, then run the checks again. Smallest change
  6. Open the pull request. Push your branch, open the PR against the project, fill in the template, write "Fixes #123" so the issue links up, and say in plain words what you changed and how you tested it. Writing a PR description
  7. Handle review, and be patient. Change requests are normal, they mean someone cares. Push fixes to the same branch. If CI fails, read the log before asking. If nobody answers in a week, one polite ping is fine. Reviews

Stuck?

Words like CLA, DCO or "upstream" are in the glossary, and the newcomer FAQ covers the usual worries. You can also ask in Discussions, someone will help.
