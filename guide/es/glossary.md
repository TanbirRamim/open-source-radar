# Glosario

| Término | Significado |
| --- | --- |
| **Assignee** | La persona responsable de un issue. Un issue asignado normalmente ya está tomado. |
| **Branch** | Una línea independiente de commits. Cada cambio lo haces en su propia rama. |
| **CI (continuous integration)** | Comprobaciones automáticas (tests, linters, builds) que se ejecutan en cada pull request. |
| **CLA (Contributor License Agreement)** | Un acuerdo legal que algunos proyectos exigen antes de aceptar contribuciones. |
| **Clone** | Una copia local del repositorio en tu ordenador. |
| **Code owner** | Una persona o equipo a la que se pide automáticamente revisar los cambios en ciertos archivos (`CODEOWNERS`). |
| **Commit** | Una instantánea guardada de los cambios, con un mensaje que los describe. |
| **Conventional Commits** | Un formato de mensaje de commit, por ejemplo `fix(parser): handle empty input`. |
| **DCO (Developer Certificate of Origin)** | Una declaración que haces añadiendo `Signed-off-by:` a tus commits (`git commit -s`). |
| **Default branch** | La rama principal de un repositorio, normalmente `main` o `master`, a veces `develop`. |
| **Draft pull request** | Un pull request marcado como aún no listo para revisión. |
| **Fork** | Tu propia copia del repositorio de otra persona, en GitHub. |
| **Force push** | Reemplazar el historial de una rama remota. Usa `git push --force-with-lease` solo en tus propias ramas. |
| **Issue** | Un reporte de error, una petición de funcionalidad o una tarea en el tracker del proyecto. |
| **Linked pull request** | Un pull request conectado a un issue, a menudo con `Fixes #123`. |
| **Linter** | Una herramienta que busca en el código problemas de estilo y errores probables. |
| **Maintainer** | Alguien con permiso para revisar y aceptar contribuciones. |
| **Merge conflict** | Cuando tu rama y la rama destino cambiaron las mismas líneas de forma distinta. |
| **Monorepo** | Un único repositorio que contiene muchos paquetes. Normalmente solo compilas y pruebas el paquete que cambias. |
| **Pull request (PR)** | Una petición de fusionar tu rama en la rama de otro repositorio. En GitLab se llama merge request. |
| **Rebase** | Volver a aplicar tus commits sobre commits más recientes, para actualizar una rama. |
| **Regression** | Un error en el que algo que funcionaba dejó de funcionar. |
| **Repository (repo)** | Los archivos de un proyecto y todo su historial. |
| **Reproduction (repro)** | Pasos o código mínimos que hacen que un error ocurra de forma fiable. |
| **Review** | Comentarios y aprobación (o cambios solicitados) de los mantenedores sobre un pull request. |
| **Squash** | Combinar varios commits en uno, algo que se suele hacer al fusionar. |
| **Stale** | Un issue o pull request sin actividad durante mucho tiempo; los bots pueden cerrarlo. |
| **Triage** | Ordenar los issues nuevos: reproducirlos, etiquetarlos, buscar duplicados. |
| **Upstream** | El repositorio original del que hiciste tu fork. |
