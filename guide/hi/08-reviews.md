# 8. Reviews, feedback और rejection

Pull Request खोल देना प्रक्रिया का अंत नहीं, बीच का पड़ाव है। आप review को कैसे संभालते हैं, इसी से तय होता है कि वह merge होगी या नहीं।

## जब CI fail हो जाए

1. जो check fail हुआ है उसे खोलें और log को आख़िरी लाइन से नहीं, **पहली error** से पढ़ना शुरू करें।
2. तय करें कि fail होने की वजह आपका बदलाव है या नहीं:
   - **Formatting या lint failure:** formatter या linter को local रूप से चलाएँ और उसका नतीजा commit करें।
   - **आपके छुए हुए किसी test का fail होना:** उसे local रूप से ठीक करें और दोबारा push करें।
   - **कोई असंबंधित test fail हो रहा है**, जो default branch पर भी fail होता है, या कोई job जो flaky लगती है (timeouts, network errors): comment में यह बात लिखें और कहीं और हुए उसी failure का link दें। जब तक कहा न जाए, असंबंधित failures को अपनी PR में ठीक करने की कोशिश न करें।
3. Fixes को नए commits के रूप में push करें, जब तक कि प्रोजेक्ट squash करने को न कहे।

कई प्रोजेक्ट्स में पहली बार योगदान करने वालों के CI runs को किसी maintainer को approve करना पड़ता है। अगर checks में "awaiting approval" दिखे, तो यह सामान्य है: इंतज़ार करें।

## जब आपको change requests मिलें

- **जवाब देने से पहले हर comment पढ़ें।** कुछ comments एक-दूसरे पर निर्भर होते हैं।
- **माँगे गए बदलाव करें, या बताएँ कि क्यों नहीं।** असहमत होना ठीक है, बशर्ते आप कारण बताएँ; किसी comment को अनदेखा करना ठीक नहीं है।
- **हर comment का जवाब दें** कि आपने क्या किया ("Done in abc123" या "Changed to use the existing helper")। Conversations को resolve करना reviewer पर छोड़ दें, जब तक कि प्रोजेक्ट कुछ और न कहे।
- **Push करें, फिर review दोबारा माँगें।** इसके लिए Pull Request पर दिए गए बटन का उपयोग करें, या एक छोटा comment छोड़ें कि अब यह फिर से तैयार है।
- **दायरा सीमित रखें।** अगर कोई reviewer बहुत बड़े बदलाव की माँग करे, तो PR को बड़ा करने के बजाय एक अलग follow-up issue का सुझाव दें।

Review comments कोड के बारे में होते हैं, आपके बारे में नहीं। किसी नए प्रोजेक्ट में अनुभवी contributors को भी कई दौर के feedback मिलते हैं।

## Automated reviewers

कुछ प्रोजेक्ट्स ऐसे bots का उपयोग करते हैं जो अपने-आप reviews पोस्ट करते हैं। उनके comments को सुझाव की तरह लें: वे जो असली समस्याएँ पकड़ें उन्हें ठीक करें, और जहाँ कोई सुझाव लागू न होता हो वहाँ विनम्रता से यह बता दें। अंतिम फ़ैसला human maintainers का होता है।

## जब कुछ भी न हो रहा हो

चुप्पी आम बात है, और इसका मतलब आम तौर पर "व्यस्त हैं" होता है, "नहीं" नहीं।

- एक-दो हफ्ते बाद एक विनम्र ping करें (अध्याय 7)।
- देखें कि प्रोजेक्ट में कोई review queue है या `waiting-on-review` जैसे labels हैं।
- अपनी branch को merge-योग्य बनाए रखें: conflicts आएँ तो उन्हें resolve करें।
- एक महीने या उससे ज़्यादा बीतने पर आप पूछ सकते हैं कि क्या यह बदलाव अब भी चाहिए। अगर नहीं, तो उसे खुद बंद कर देना ठीक है और सराहनीय भी।

## जब आपकी Pull Request बंद कर दी जाए

यह सबके साथ होता है। आम कारण:

| कारण | क्या करें |
| --- | --- |
| किसी और ने पहले ठीक कर दिया | अपनी PR बंद करें, उन्हें धन्यवाद दें, और अगली बार issue आने के बाद जल्दी कोई दूसरा issue चुनें |
| Maintainers कोई दूसरा तरीका चाहते हैं | पूछें कि क्या वे संशोधित version स्वीकार करेंगे, या उन्हें अपने तरीके से करने दें |
| प्रोजेक्ट के दायरे से बाहर है | इसे स्वीकार करें; पूछें कि क्या plugin या अलग package बनाना ठीक रहेगा |
| गुणवत्ता कम या अस्पष्ट | Feedback को ध्यान से पढ़ें; उस प्रोजेक्ट में आपकी अगली PR साफ़ तौर पर बेहतर होनी चाहिए |
| Automation ने बंद की | Bot का संदेश और workflow file पढ़ें; जो वह माँग रहा है उसे ठीक करें या maintainers से संपर्क करें |
| कोई जवाब नहीं आया, stale मानकर बंद हुई | विनम्रता से पूछें कि क्या वे इसे दोबारा खोलना चाहेंगे; नहीं तो आगे बढ़ जाएँ |

विनम्र और रचनात्मक जवाब के साथ बंद हुई Pull Request भी अच्छी छाप छोड़ती है।

## Merge के बाद

- अपनी branch delete कर दें (GitHub इसके लिए बटन देता है)।
- अपने fork की default branch को update करें: `git fetch upstream && git switch main && git rebase upstream/main && git push`।
- ध्यान दें कि आपने उस प्रोजेक्ट की प्रक्रिया के बारे में क्या सीखा। वहाँ आपकी दूसरी Pull Request कहीं ज़्यादा तेज़ी से पूरी होगी।

## चेकलिस्ट

- [ ] मैंने CI logs को पहली error से पढ़ा, और अपने failures को पहले से मौजूद failures से अलग पहचाना।
- [ ] मैंने हर review comment का जवाब दिया और review दोबारा माँगा।
- [ ] मैंने Pull Request का दायरा छोटा रखा।
- [ ] मैंने विनम्रता से follow up किया, हफ्ते में एक बार से ज़्यादा नहीं।
