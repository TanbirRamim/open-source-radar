# 3. एक प्रोजेक्ट चुनें

प्रोजेक्ट issue से ज़्यादा मायने रखता है। एक स्वागत करने वाला, सक्रिय प्रोजेक्ट आपके pull request की समीक्षा कुछ दिनों में कर देगा। एक निष्क्रिय या ज़्यादा भार वाला प्रोजेक्ट उसे कभी नहीं देख सकता, चाहे वह कितना भी अच्छा हो।

## जो आप इस्तेमाल करते हैं उसी से शुरू करें

सबसे अच्छा पहला प्रोजेक्ट वही है जो आप पहले से इस्तेमाल करते हैं: अपने कोड में कोई लाइब्रेरी, रोज़ चलाने वाला कोई टूल, कोई ऐप जो आपको पसंद है। आप जानते हैं उसे क्या करना चाहिए, आप अपने बदलाव को सच में टेस्ट कर सकते हैं, और आपको नतीजे की परवाह है।

अगर कुछ याद नहीं आता, तो जिस भाषा में आप सबसे अच्छे हैं उसके हिसाब से [issue index](../issues/README.md) ब्राउज़ करें, और देखें कौन-से प्रोजेक्ट बार-बार दिखते हैं।

## एक स्वस्थ, स्वागत करने वाले प्रोजेक्ट के संकेत

ये रिपॉज़िटरी पेज पर जाँचें। यहाँ पाँच मिनट बिताने से हफ़्तों की प्रतीक्षा बचती है।

| जाँच | कहाँ देखें | अच्छा संकेत |
| --- | --- | --- |
| हाल की गतिविधि | Commits टैब, "last commit" तारीख़ | पिछले कुछ हफ़्तों में commits |
| बाहरी योगदान merge हुए | **Pull requests → Closed**, `is:merged` फ़िल्टर करें और लेखक देखें | पिछले महीने उन लोगों के pull requests merge हुए जो maintainer नहीं हैं |
| समीक्षा की गति | बाहरी लोगों के कुछ हाल में merge हुए PR खोलें | पहला जवाब कुछ दिनों में, महीनों में नहीं |
| योगदान गाइड | रूट, `.github/` या `docs/` में `CONTRIBUTING.md` | मौजूद है और setup व testing समझाता है |
| नए लोगों के लेबल | Issues, `good first issue` या `help wanted` से फ़िल्टर करें | लेबल इस्तेमाल होते हैं, और लेबल वाले issues उठाए जाते हैं |
| लहज़ा | कुछ issue थ्रेड पढ़ें | Maintainers धैर्य और विशिष्टता से बात करते हैं, मना करते समय भी |
| आचार संहिता | `CODE_OF_CONDUCT.md` | मौजूद है |
| CI | हाल के PR पर checks | pull requests पर टेस्ट अपने आप चलते हैं |

एक त्वरित खोज जो किसी भी रिपॉज़िटरी के बाहरी योगदानकर्ताओं के merge हुए PR दिखाती है (`OWNER/REPO` बदलें):

```text
https://github.com/OWNER/REPO/pulls?q=is:pr+is:merged+-author:app/dependabot+sort:updated-desc
```

लेखकों को देखें: अगर हर merge हुआ PR उन्हीं दो लोगों का है, तो बाहरी योगदान वहाँ प्राथमिकता नहीं हो सकता।

## चेतावनी के संकेत

- **सैकड़ों खुले pull requests बिना समीक्षा के।** आपका भी कतार में शामिल हो जाएगा।
- **ऐसा योगदान गाइड जो कहता है कि प्रोजेक्ट pull requests नहीं ले रहा**, या सिर्फ़ किसी ख़ास लेबल वाले issues के लिए लेता है। कुछ लोकप्रिय प्रोजेक्ट ऐसे ही चलते हैं। इसका सम्मान करें।
- **हर हाल के issue पर पहले से कई मुकाबले वाले pull requests।** लोकप्रिय प्रोजेक्ट में bug दर्ज होने के कुछ घंटों के भीतर ही drive-by PR आ जाते हैं। आप वहाँ योगदान कर सकते हैं, लेकिन कम मुकाबले वाला काम चुनें (docs, tests, पुराने पुष्ट bug) या छोटा प्रोजेक्ट।
- **Maintainers लोगों से कम मेहनत वाले pull requests बंद करने को कह रहे हों।** वे थ्रेड पढ़ें: वे साफ़ बताते हैं कि क्या नहीं करना है।
- **महीनों से कोई commit नहीं।** प्रोजेक्ट पूरा हो सकता है, या छोड़ दिया गया हो।

## बड़ा प्रोजेक्ट या छोटा प्रोजेक्ट?

| | बड़ा, प्रसिद्ध प्रोजेक्ट | छोटा, सक्रिय प्रोजेक्ट |
| --- | --- | --- |
| आसान issues पर मुकाबला | बहुत ज़्यादा | कम |
| समीक्षा की गति | बहुत बदलती है; बाहरी लोगों के लिए अक्सर धीमी | अक्सर तेज़ और व्यक्तिगत |
| प्रक्रिया | औपचारिक: templates, CLAs, सख़्त CI | हल्की |
| मार्गदर्शन | कभी-कभी संरचित कार्यक्रम होते हैं | maintainer से सीधा संपर्क |
| आपकी प्रोफ़ाइल पर संकेत | नाम की मज़बूत पहचान | मज़बूत, अगर आप नियमित बनें |

एक अच्छी रणनीति: अपने पहले एक-दो योगदान किसी छोटे, सक्रिय प्रोजेक्ट में करें जहाँ आपको तेज़ प्रतिक्रिया मिले, फिर जो सीखा उसे बड़े प्रोजेक्ट में ले जाएँ।

## चेकलिस्ट

- [ ] प्रोजेक्ट में पिछले महीने commits थे।
- [ ] उसने हाल में बाहरी योगदानकर्ताओं के pull requests merge किए।
- [ ] उसका योगदान गाइड है, और मैंने उसे पढ़ लिया है।
- [ ] मैं इसे अपनी मशीन पर build और run कर सकता/सकती हूँ (अध्याय 5 इसे कवर करता है)।
