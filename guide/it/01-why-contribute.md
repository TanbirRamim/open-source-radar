
# 1. Perché contribuire e cosa significa

## Cosa ottieni

- **Esperienza nel mondo reale.** Lavori su basi di codice utilizzate da migliaia di persone e ricevi revisioni del codice da parte di ingegneri esperti. Pochi corsi o progetti personali possono offrirti un'esperienza simile.
- **Un percorso professionale documentato pubblicamente.** Le pull request unite al progetto sono prove concrete e consultabili delle tue capacità. Anche i responsabili delle assunzioni possono esaminarle.
- **Competenze migliori, più rapidamente.** Leggere il codice scritto da altre persone, seguire le convenzioni del progetto e ricevere feedback dettagliati ti insegna molto più che scrivere codice da solo.
- **Relazioni professionali.** I maintainer e i collaboratori abituali possono diventare colleghi, mentori e referenti professionali.
- **Migliorare ciò che utilizzi.** Il bug che dà fastidio a te probabilmente crea problemi anche ad altre persone.

## Come si contribuisce concretamente

La maggior parte dei primi contributi è di piccole dimensioni. Una correzione di una sola riga accompagnata da un buon test è un'ottima prima pull request. Lo stesso vale per un messaggio di errore più chiaro, un esempio mancante nella documentazione oppure una procedura di riproduzione che trasforma una segnalazione vaga in un problema su cui un maintainer può intervenire.

## Contributi che non richiedono codice

Questi contributi sono davvero apprezzati e spesso più difficili da trovare rispetto a quelli basati sul codice:

| Contributo | Perché è importante |
| --- | --- |
| Riproduzione delle segnalazioni di bug | I maintainer dedicano molto tempo a chiedere: "Puoi indicarmi i passaggi per riprodurre il problema?". Una riproduzione chiara nella segnalazione evita loro questo lavoro. |
| Triage | Segnalare problemi duplicati, confermare un bug nell'ultima versione oppure indicare che un problema è già stato risolto. |
| Documentazione | Correggere istruzioni errate, aggiungere esempi mancanti e spiegare opzioni poco chiare. |
| Traduzioni | Molti progetti hanno bisogno di traduttori e dispongono di strumenti dedicati per gestire le traduzioni. |
| Test | Aggiungere test per comportamenti non ancora verificati oppure trasformare una segnalazione di bug in un test che inizialmente fallisce. |
| Revisione del codice | Quando conosci bene un progetto, revisionare attentamente le pull request di altri collaboratori è un contributo prezioso. |
| Design, accessibilità e UX | Molti progetti non dispongono di designer o di persone che possano verificare l'accessibilità. |
| Rispondere alle domande | Aiutare altri utenti nelle discussioni, nei forum o nelle chat è un altro modo di contribuire. |

## Aspettative da avere

- La tua prima pull request probabilmente richiederà più tempo del previsto, soprattutto per la configurazione dell'ambiente e la lettura del codice. È del tutto normale.
- Alcune pull request non vengono mai unite al progetto. Spesso i motivi non hanno nulla a che fare con la qualità del tuo codice: il maintainer è impegnato, la direzione del progetto è cambiata oppure qualcun altro ha già risolto il problema. Il capitolo 8 approfondisce questo argomento.
- La costanza conta più della quantità. Cinque pull request unite nello stesso progetto ti insegnano di più e rappresentano un risultato migliore rispetto a una pull request in ciascuno di cinquanta progetti diversi.

## Lista di controllo

- [ ] So quale tipo di contributo voglio realizzare per primo (codice, documentazione, test o triage).
- [ ] Ho individuato uno o due progetti che utilizzo davvero o a cui tengo.
- [ ] Ho intenzione di iniziare con un piccolo contributo, non con una grande funzionalità.
