# Glossário

| Termo | Significado |
| --- | --- |
| **Assignee** | A pessoa responsável por uma issue. Uma issue atribuída geralmente já foi assumida por alguém. |
| **Branch** | Uma linha independente de commits. Cada alteração deve ser feita em sua própria branch. |
| **CI (continuous integration)** | Verificações automatizadas (testes, linters e builds) executadas a cada pull request. |
| **CLA (Contributor License Agreement)** | Um acordo legal que alguns projetos exigem antes de aceitar contribuições. |
| **Clone** | Uma cópia local de um repositório no seu computador. |
| **Code owner** | Uma pessoa ou equipe que é automaticamente solicitada a revisar alterações em determinados arquivos (`CODEOWNERS`). |
| **Commit** | Um snapshot salvo das alterações, acompanhado de uma mensagem que as descreve. |
| **Conventional Commits** | Um formato padronizado para mensagens de commit, como `fix(parser): handle empty input`. |
| **DCO (Developer Certificate of Origin)** | Uma declaração que você faz ao adicionar `Signed-off-by:` aos commits (`git commit -s`). |
| **Default branch** | A branch principal de um repositório, geralmente `main` ou `master`, e às vezes `develop`. |
| **Draft pull request** | Um pull request marcado como ainda não pronto para revisão. |
| **Fork** | Uma cópia própria de um repositório de outra pessoa ou organização no GitHub. |
| **Force push** | A substituição do histórico de uma branch remota. Use `git push --force-with-lease` apenas em suas próprias branches. |
| **Issue** | Um relatório de bug, solicitação de funcionalidade ou tarefa no rastreador de um projeto. |
| **Linked pull request** | Um pull request conectado a uma issue, geralmente usando algo como `Fixes #123`. |
| **Linter** | Uma ferramenta que verifica problemas de estilo e possíveis erros no código. |
| **Maintainer** | Alguém que tem permissão para revisar e fazer merge de contribuições. |
| **Merge conflict** | Ocorre quando sua branch e a branch de destino modificaram as mesmas linhas de maneiras diferentes. |
| **Monorepo** | Um único repositório que contém vários pacotes. Normalmente, você compila e testa apenas o pacote que foi alterado. |
| **Pull request (PR)** | Uma solicitação para mesclar sua branch em uma branch de outro repositório. No GitLab, é chamado de merge request. |
| **Rebase** | O processo de reaplicar seus commits sobre commits mais recentes, atualizando sua branch. |
| **Regression** | Um bug em que algo que funcionava anteriormente deixa de funcionar. |
| **Repository (repo)** | Os arquivos de um projeto e todo o seu histórico. |
| **Reproduction (repro)** | Um conjunto mínimo de passos ou código que faz um bug acontecer de forma confiável. |
| **Review** | Comentários e aprovação (ou solicitação de alterações) dos maintainers em um pull request. |
| **Squash** | Combinar vários commits em um único commit, geralmente feito durante o merge. |
| **Stale** | Uma issue ou pull request sem atividade por um longo período; bots podem fechá-la automaticamente. |
| **Triage** | O processo de organizar novas issues: reproduzir problemas, adicionar labels e identificar duplicatas. |
| **Upstream** | O repositório original do qual você fez o fork. |
