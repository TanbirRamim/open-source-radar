# 1. Por que contribuir, e o que conta

## O que você ganha

- **Experiência de mundo real.** Você trabalha em codebases que servem milhares de usuários, com revisão de código de engenheiros experientes. Poucos cursos ou projetos pessoais oferecem isso.
- **Um histórico público.** Pull requests aceitos são prova visível e linkável do que você sabe fazer. Recrutadores leem isso.
- **Habilidades melhores, mais rápido.** Ler o código dos outros, seguir as convenções deles e receber feedback linha por linha ensina mais do que programar sozinho.
- **Pessoas.** Mantenedores e contribuidores regulares viram colegas, mentores e referências.
- **Consertar coisas que você usa.** O bug que irrita você provavelmente irrita outra pessoa também.

## Como contribuir se parece na prática

A maioria das primeiras contribuições é pequena. Corrigir um bug de uma linha com um bom teste é um ótimo primeiro pull request. Assim como uma mensagem de erro mais clara, um exemplo faltando na documentação, ou uma reprodução que transforma um relato vago de bug em algo com que o mantenedor consegue agir.

## Contribuições que não são código

Elas são genuinamente valorizadas, e muitas vezes mais raras do que código:

| Contribuição | Por que importa |
| --- | --- |
| Reproduzir relatos de bug | Mantenedores gastam muito tempo perguntando "você pode dar os passos para reproduzir?". Uma reprodução clara na issue poupa esse trabalho. |
| Triagem | Apontar duplicatas, confirmar um bug na versão mais recente, ou notar que algo já foi corrigido. |
| Documentação | Corrigir instruções erradas, adicionar exemplos faltando, explicar uma opção confusa. |
| Traduções | Muitos projetos precisam de tradutores e têm ferramentas dedicadas para isso. |
| Testes | Adicionar cobertura para comportamento não testado, ou transformar um relato de bug em um teste que falha. |
| Revisar | Quando você conhece um projeto, revisões cuidadosas dos pull requests de outras pessoas são valiosas. |
| Design, acessibilidade, UX | Muitos projetos não têm designers nem testadores de acessibilidade. |
| Responder perguntas | Em discussões, fóruns ou chat, ajudar outros usuários é uma contribuição. |

## Expectativas para ter consigo mesmo

- Seu primeiro pull request provavelmente vai demorar mais do que você espera, a maior parte em configuração e leitura. Isso é normal.
- Alguns pull requests nunca são aceitos. Os motivos muitas vezes não têm nada a ver com a qualidade do seu código: o mantenedor está ocupado, a direção mudou, outra pessoa corrigiu antes. O capítulo 8 cobre isso.
- Consistência vence volume. Cinco pull requests aceitos em um projeto ensinam mais, e ficam melhor, do que um pull request em cada um de cinquenta projetos.

## Lista de verificação

- [ ] Sei que tipo de contribuição quero fazer primeiro (código, docs, testes, triagem).
- [ ] Tenho um ou dois projetos em mente que eu realmente uso ou pelos quais me importo.
- [ ] Estou planejando uma primeira contribuição pequena, não uma grande funcionalidade.
