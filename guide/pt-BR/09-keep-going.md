# 9. Continue

Um pull request mesclado é um ótimo começo. O que realmente constrói habilidades e reputação é se tornar alguém frequente em algum lugar.

## Vá mais fundo, não mais largo

Depois da sua primeira contribuição a um projeto, faça outra lá. Seu segundo pull request é muito mais rápido: você já conhece a configuração, os testes, as convenções e as pessoas. No quinto, mantenedores reconhecem seu nome e revisam mais rápido.

Sinais de que você está se tornando frequente:

- Mantenedores mencionam você em issues da sua área.
- Você consegue fazer triagem de novas issues: reproduzi-las, etiquetá-las, apontar duplicatas.
- Outros contribuidores fazem perguntas para você.

## Amplie suas contribuições

Uma progressão natural:

1. **Correções de bugs e documentação** com escopo claro.
2. **Testes** para áreas não cobertas e **triagem** de novas issues.
3. **Pequenas funcionalidades** que mantenedores já concordaram em uma issue.
4. **Revisões** de pull requests de outras pessoas. Pergunte primeiro se revisões externas são bem-vindas.
5. **Trabalho maior:** propostas de design, refatorações, releases. Discuta isso antes de escrever código.

## Programas que pagam ou orientam contribuidores

Eles mudam com o tempo, então verifique o site de cada programa para datas e elegibilidade atuais:

- [Google Summer of Code](https://summerofcode.withgoogle.com): projetos de verão pagos e orientados com organizações de código aberto.
- [Outreachy](https://www.outreachy.org): estágios pagos para pessoas de grupos sub-representados em tecnologia.
- [LFX Mentorship](https://mentorship.lfx.linuxfoundation.org): projetos orientados na Linux Foundation e em projetos CNCF.
- [GitHub Sponsors](https://github.com/sponsors): alguns mantenedores e contribuidores recebem patrocínio depois de estabelecidos.
- Muitas fundações e empresas executam seus próprios programas ou recompensas; os READMEs dos projetos geralmente os vinculam.

## Mostrando seu trabalho

- Fixe (pin) suas melhores contribuições no seu perfil do GitHub, ou liste-as em um README de perfil.
- Vincule pull requests mesclados específicos no seu currículo, não só o perfil: "Corrigi um loop infinito no prompt de login (owner/projeto#1234)".
- Escreva sobre o que aprendeu. Um post curto sobre depurar um problema real em um projeto real é interessante de ler.

## Começando seu próprio projeto

Quando você publica algo seu, as coisas que tornaram os projetos acolhedores para você se aplicam ao contrário: um README com etapas de configuração, um `CONTRIBUTING.md`, uma licença, etiquetas de issues para iniciantes e respostas rápidas e gentis às primeiras pessoas que aparecerem.

## Evite o esgotamento

- Contribua quando for sustentável para você. Código aberto não é um emprego a menos que alguém te pague.
- Tudo bem se desatribuir de uma issue que você não consegue terminar. Diga isso na issue.
- Tudo bem fazer pausas.
