# 1. Why contribute, and what counts

## What you get

- **Real-world experience.** You work in codebases that serve thousands of users, with code review from experienced engineers. Few courses or side projects give you that.
- **A public track record.** Merged pull requests are visible, linkable proof of what you can do. Hiring managers read them.
- **Better skills, faster.** Reading other people's code, following their conventions and getting line-by-line feedback teaches you more than writing code alone.
- **People.** Maintainers and regular contributors become colleagues, mentors and references.
- **Fixing things you use.** The bug that annoys you is probably annoying someone else too.

## What contributing actually looks like

Most first contributions are small. A one-line bug fix with a good test is a great first pull request. So is a clearer error message, a missing example in the docs, or a reproduction that turns a vague bug report into something a maintainer can act on.

## Contributions that are not code

These are genuinely valued, and often scarcer than code:

| Contribution | Why it matters |
| --- | --- |
| Reproducing bug reports | Maintainers spend a lot of time asking "can you give me steps to reproduce?". A clear reproduction on the issue saves them that. |
| Triage | Pointing out duplicates, confirming a bug on the latest version, or noting that something is already fixed. |
| Documentation | Fixing wrong instructions, adding missing examples, explaining a confusing option. |
| Translations | Many projects need translators and have dedicated tooling for it. |
| Tests | Adding coverage for untested behaviour, or turning a bug report into a failing test. |
| Reviewing | Once you know a project, careful reviews of other people's pull requests are valuable. |
| Design, accessibility, UX | Many projects lack designers and accessibility testers. |
| Answering questions | In discussions, forums or chat, helping other users is a contribution. |

## Expectations to set for yourself

- Your first pull request will probably take longer than you expect, mostly in setup and reading. That is normal.
- Some pull requests are never merged. The reasons are often unrelated to your code quality: the maintainer is busy, the direction changed, someone else fixed it first. Chapter 8 covers this.
- Consistency beats volume. Five merged pull requests in one project teach you more, and look better, than one pull request in each of fifty projects.

## Checklist

- [ ] I know what kind of contribution I want to make first (code, docs, tests, triage).
- [ ] I have one or two projects in mind that I actually use or care about.
- [ ] I am planning for a small first contribution, not a big feature.
